# code-write-read

コードを「書く(write)」ときも「読む(read)」ときも、同じ物差しを当てるための Claude Skill。
『リーダブルコード』(可読性の軸)と『良いコード/悪いコードで学ぶ設計入門』(設計の軸)の原則をベースにしている。

## これは何をするスキルか

- コードを **生成・修正・リファクタリング** するとき → 原則を黙ってコードに反映させる(説明はしない)
- コードを **レビュー・説明** するとき → 指摘を重要度別(XXX / FIXME / HACK / TODO)に分類して出力する

「書く」と「読む」を別々のスキルにせず1つにまとめているのは、両方とも同じ判断基準(可読性の軸・設計の軸)を使うため。

## インストール

### claude.ai
1. 設定 → Capabilities(または Skills)から `code-write-read.skill` をアップロード
2. 常時オンで効かせたい場合は、ユーザー設定の「個人の指示」に一文加える:
   > コードを書く・読むときは常に code-write-read スキルに従う

### Claude Code
1. `code-write-read/` フォルダを `~/.claude/skills/`(個人用)または `.claude/skills/`(プロジェクト用)に置く
2. `.skill` ファイルから展開する場合は zip として解凍する
3. 確実に効かせたい場合は `CLAUDE.md` に同様の一文を追加する

## ファイル構成

```
code-write-read/
├── SKILL.md                      本体。モード判定、Write/Read の原則、出力フォーマット
├── README.md                     このファイル
└── references/
    ├── readable-code.md          可読性の軸: 命名・コメント・制御フロー・式・変数の詳細と例
    ├── design.md                 設計の軸: 凝集度・結合度・値オブジェクト・条件分岐整理などの詳細と例
    └── language-notes.md         TS/JS, Go, Python, Java, Rust, C++, Ruby, Kotlin, C# の言語別の当てはめ方
```

SKILL.md 本体には頻出する原則名の語彙集を載せてあるので、通常の指摘は参照ファイルを開かなくても書ける。参照ファイルは、設計上の判断に迷ったときや言語固有の慣習(Rust の所有権、C++ の RAII など)を確認したいときに読みに行く。

## 発動条件と出力の重さ

発動すること自体は広く取っている(コードに関わる作業なら基本的に発動する)。ただし出力の重さは作業の規模で変える。

| 規模 | 例 | 振る舞い |
|---|---|---|
| 軽微 | typo修正、変数名1つの変更 | コードを直すだけ。フルレポートは出さない |
| 通常 | 数十行規模の関数追加・修正 | 依頼範囲に閉じた簡潔な指摘 |
| 大きい/明示的な依頼 | 新規実装、レビュー依頼、リファクタリング依頼 | フルレポート |

## 出力フォーマットの例

### Write(コード生成・修正)
コードのみを返す。原則を適用した理由の説明はしない。ただし原則から意図的に外した箇所があれば1行だけ添える。

### Read(レビュー・説明)
```
## Write/Read チェック: calculateDiscount()
概要: 注文の割引額を会員種別に応じて計算する

### XXX (1)
- **L12** 割引率が0未満でも例外を投げずに計算を続けている。不正な設定値が入ると負の金額を請求しうる。
  → 生成時にガード節で弾く 〔完全コンストラクタ〕

### TODO (2)
- **L3** `d` という汎用的な変数名。用途が分かる名前にする 〔汎用名を避ける〕
- **L20** ネストが3段。ガード節で浅くできる 〔早期return〕

### 最初に直すべきもの
1. L12 の負の割引率チェック
```

既定は絵文字なしのプレーンテキスト。チームで別の形式(PRコメント形式、severity: high/medium/low など)を使っている場合はそれに合わせてよい。分類の判断基準(下記)自体は変えない。

## 重要度の判断基準

「放置したら何が起きるか」で決める。

| タグ | 放置した結果 |
|---|---|
| XXX | 障害・データ破損・セキュリティ問題につながりうる |
| FIXME | 次に触る人が間違った変更をしやすい |
| HACK | 変更のたびにコストが膨らむ(動くが設計が弱い) |
| TODO | 読むのに余計な時間がかかるだけ |

## カスタマイズ

- **チームの規約を優先させたい**: SKILL.md の「出力フォーマット」節に、使いたい形式を書き足す、または会話内で「うちは severity: high/medium/low で」のように伝えれば従う
- **対象言語を増やしたい**: `references/language-notes.md` に節を追加する
- **重要度の基準を変えたい**: SKILL.md の「重要度の定義」表を編集する
- **もっと軽くしたい/重くしたい**: SKILL.md の「適用の程度」表のしきい値を調整する

## 既知の限界

- 発動判定はモデルの解釈に依存するため、必ず100%狙い通りに発動するとは限らない
- Rust/C++/Ruby/Kotlin/C# の言語ノートは TS/JS・Go・Python・Java ほど厚くない
- フォーマッタ/リンタが直せる指摘(インデント・空白など)は対象外
